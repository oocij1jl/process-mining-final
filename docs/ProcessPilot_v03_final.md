## 1. Product promise and acceptance

**Discover how work flows. Design how it should flow.** A general-purpose, browser-based visual process intelligence tool. From a real or synthetic event log, discover recorded process behavior, investigate delays and repeats, understand organizational handovers, compare with reference BPMN, design improvements and evaluate their effects. Music Festival Operations & Resource Optimization is a case study, not a restriction on general analysis.

Sources: Week 1 pp.7–12,15–17 (PI and lifecycle); Weeks 2–4 (BPMN activities, events, gateways, swimlanes and connectors); Week 5 pp.7–11 (BPMN.io and business context); Weeks 6–7 (BPMS, actors, organization, business data); Week 9 pp.8–20 and ICN/WTN sections (log discovery, process reality, organizational networks); Week 10 p.42 (unique business process, BPMN, generated event log, process discovery, analysis, improvements, report and video); Week 11 pp.14–21 (GUI supporting lifecycle, illustrative features). Week 8 not supplied. Professor ProcessLens feature descriptions are student-provided, not independently verified implementation details. They inform lifecycle separation, not visual copying or claims of exclusivity.

The eight approved analysis questions must remain visible in the product:

| Question | Function | Primary workspace |
|---|---|---|
| What sequence does work actually follow? | Process Discovery | Analysis |
| Which path is most common? | Variant Analysis | Analysis |
| Where does work take longer? | Performance Map | Analysis |
| Which activities are repeated? | Rework Analysis | Analysis |
| Who hands work over to whom? | WTN-inspired Network | Analysis |
| How does the reference process differ from recorded behavior? | BPMN & Discovered Model Comparison | Model, linked from Analysis |
| How could the process be improved? | To-be Modeling | Design → Model |
| What would change under a proposed improvement? | What-if Simulation | Refine & Improve |

Additional capabilities: Event Log Replay, Automation & ROI, historical performance and transition drift, deadline risk if supported. Distinctive focus: organizational mining, ICN-inspired evidence, clickable evidence chain, multi-process Festival relationships, transparent metrics/assumptions. Do not claim these are absent in ProcessLens.

## 2. Global UI / UX

English interface (course language). Retain six lifecycle names; plain-language subtitles and one primary next action per page. Use existing React/TS/Tailwind/React Flow/Recharts/bpmn-js stack. No backend or runtime LLM by default. Modern coherent light workspace, restrained indigo accent, neutral surfaces, orange/red only for meaningful warnings. 1440px desktop first, responsive at smaller widths. Avoid excessive card borders, huge headers, tiny labels, crowded toolbars, and tables as the default presentation. Consistent spacing, accessible contrast, keyboard focus, non-color status labels. Graph canvas ~65–75% and inspector ~25–35% (drawer on narrow screens), at least ~450px height; fit, zoom, pan, fullscreen if practical. Use readable activity labels, direction arrows, edge width/count, legend, and avoid overlaps. Preserve viewport when inspector opens. Use chart/table views as complementary detail.

Header: selected dataset/process, explicit synthetic/uploaded source, whole-case date scope; compact breadcrumbs. Overview default sample or one-click sample selection; graph visible in at most two interactions from fresh browser. No dev terminology (Fixture, Provider, fingerprint, engine function status) in primary flow; retain diagnostics under Data Details/Advanced. Source/provenance still visible. No fake buttons, stale numbers, or unsupported metrics shown as zero. Empty states explain missing prerequisites and next action. Loading progress or busy state for computation, errors recoverable. Keep UI state scope, archive and prior records; do not conflate provider, dataset, process, filter, or simulation revision. Keep current routes or provide aliases and migration. Store no raw uploaded data without consent; no external API keys in client.

End-to-end evidence chain: click graph node/edge → case list → actual trace/timeline → finding → redesign strategy → To-be model or proposal → what-if → prioritized rollout → monitoring/next cycle. Each saved object keeps scope and linked evidence IDs. No hardcoded outcomes. Clicking from one page should restore relevant selection, not force re-entry.

## 3. Screen requirements and ownership

### Overview & Data — Start with a business question

Festival sample with Stage, Audience and Equipment process chooser, case meaning, purpose, actors, start/end, business rules and explicit generation provenance. One-click load and Explore. Upload CSV, mapping, validation, consent/exclusions retained. XES optional, with explicit small-file limit and supported fields. No course dataset redistribution.
- Summaries: cases, raw events, discovery instances/activities, observed elapsed span, top variant; definitions distinguish observed span from true completion. No test-only datasets as primary demo once final assets available.

### Analysis — Discover & diagnose
- Graph-first workspace: Frequency (node instances and direct transition count), Performance (separate mean inter-event gap, matched gap, and matched service time; n and coverage), Variants (path chips, count/share/elapsed, select → highlight and cases), WTN (direct handover graph, resource identity, coverage and workload), Rework (repeat counts and cases), Patterns, Replay. Preserve current calculations. Display-only minimum edge-count filter for DFG and WTN: report hidden/total edges; never change underlying analysis or export. Graph and table must agree. Start/end evidence via I-2. Findings panel shows observation, metric definition, evidence, low support, suggested next action; avoid causal claims.
- Rework: repeated occurrence of same discovery activity within case, not start/complete pair; report repeated cases / cases with nonempty sequence, extra occurrence count, per-activity evidence. Generic repetition is not automatically an error; explicitly configured Festival recheck is separate.
- WTN: immediate consecutive complete/point events with known distinct resources; preserve existing missing/same-resource exclusion. No claim of exact KGU WTN algorithm. Resource graph selection identifies actual paired activities/cases; do not equate handover with causal communication. Do not infer staffing overload without capacity/shift evidence.
- Pattern Explorer (priority extension): sequential observed edges, divergence alternatives, self-loop and A→B→A patterns, matched lifecycle overlap evidence within same case. Both orders alone do not prove AND; choices are candidates, not proven XOR/OR. Label ICN-inspired, not full rho/ICN.
- Event Log Replay (priority extension): time cursor, play/pause, speed, scrub, time window, variant filter, token counts and selected case. Derive states from original ordered events and case scope; replay window includes cases already active at its start. Complete/point-only tokens indicate latest recorded activity; no invented waiting or interpolated service. Matched start/complete can indicate observed active interval. Equal timestamp uses source order; cases not yet started absent; completed only if terminal definition known, otherwise last observation. Animation is visualization, not token-based conformance. For large logs aggregate visible tokens and display exact counts, disclose sampling if used.
- Deviation: exact activity mapping proposal, user edit, unmapped/ambiguous activity labels and reference-only activities; direct allowed adjacency check only on supported simple sequential/XOR structures, traversing silent supported gateway/event nodes. Parallel/inclusive/subprocess/complex/ambiguous models warn unsupported, no false fitness score. Link to Model comparison. Minimum release: truthful visual comparison + mapping coverage.

### Design — Redesign Strategy

Use rule-based templates, no runtime AI claim. Optional export/copy of external AI prompt, not necessary for release.
- Do not propose removing safety checks or parallelizing dependent activities as proven solutions. Candidate impact only via supported simulation or user assessment. Target KPI selection must map to actual metric; otherwise prompt user. Existing Design records retained, migrated or readable via history. Primary action: Open Model or Evaluate scenario.

### Model — BPMN Modeling Studio
- As-is reference, observed DFG and To-be distinct. Compare panels/tabs with task mapping and evidence; selecting BPMN task links mapped log cases/time/count. Original As-is immutable unless user explicitly edits/saves new reference version. To-be copy editable using existing bpmn-js Modeler, local verify import and CSS. Start/end, tasks, XOR/AND/OR, sequence flow, pools/lanes through native palette; rename/move/connect, undo/redo. Import/edit/save/export/reimport BPMN 2.0 with DI. Separate saved revisions; refresh restore with size limit/consent or explicit reload guidance. If Modeler fails, retain viewer and external edit/reimport, no fake editor. BPMN editing does not automatically change simulation or prove performance improvement.
- Move KPI objective setting to Design/Monitor, simulation params to Refine. Existing data records and links retained. No full BPMN execution engine or automatic gateway inference.

### Implementation — Automation & Rollout
- Activity list from actual discovery engine. Distinguish logged frequency, extra repeat counts, matched mean and total service times (coverage shown) from user assessment of rule-based work, digital readiness, human judgment, implementation difficulty, safety risk. Candidate score is transparent heuristic, not AI prediction. Proposed default for technical freeze: workload opportunity = average of frequency / max activity frequency and known total service / max known total service (scale 0–100; if service absent show frequency-only proxy explicitly). Suitability = mean of 3 user inputs 0–5 (rule-based, digital readiness, low need for human judgment), scaled 0–100; unassessed inputs → not scored. Final score = equal-weight opportunity and suitability; risk gate separately requires human review for high safety risk or missing risk assessment, never automatically recommend unsafe removal. Difficulty is separate, not hidden inside score. Show weights/denominators; compare only comparable evidence, label proxy. Freeze exact formula with Codex before implementation; no arbitrary fabricated score defaults.
- Benefit estimator: volume V for user-defined period, eligible share c (0–1), current service seconds t0 from valid matched observations or explicit user assumption, expected post-change seconds t1, hours released = V*c*(t0−t1)/3600. Allow negative benefit if slower. Labor capacity value = hours × hourly cost; label capacity value, not necessarily cash savings. Realizable fraction user-defined if monetary ROI requested; benefit = capacity value × realization fraction + explicitly entered independent benefit (avoid double count). Total cost = initial + recurrent for same period; net = benefit − cost; ROI = net / cost ×100 for positive cost only. Missing costs/realization → ROI N/A, time estimate may remain available. Currency one consistent input unit. No auto annualization or invented wage/cost. For nonautomation improvements allow user-entered benefits/costs or linked scenario's actual modeled change; waiting time reduction is not labor savings.
- Impact–difficulty matrix: user-rated impact and difficulty on explicit 1–5 scale (or quantitative impact displayed separately), both required to classify. Suggested quadrants high≥4, low≤3; risk gate overrides priority; order by user decision, not false optimizer. Matrix and ranked list link to candidate and evidence. Plan from selected candidate/scenario (owner, due, status, staffing if supported, steps, acceptance check). Existing Action Plan/Archive preserved; no actual execution or forced download. Export lives in Evidence Export.

### Monitor & Control — Track & detect change
- Historical KPI definition, measured value, n/eligible/denominator, target direction and status, evidence, observed/synthetic provenance. No KPI targets invented as industry standards. Trend by explicit time bucket, based on whole-case first timestamp for observed span/repeat summaries or selected terminal event timestamp for throughput; label assignment semantics. Observed case span ≠ completion duration unless terminal status known. Empty buckets N/A for mean/rate without denominator; 0 only for count within observed window. Generic completion/success terminal activity mapping user-defined, N/A until defined. Same units/scope definitions for baseline/recent.
- Transition drift (extension): compare two user-selected non-overlapping periods, transition share = count(A→B)/all outgoing transitions from A per period, delta percentage points; mean inter-event gap delta separately, n shown, zero denominator N/A, low support label. This is descriptive change, not statistical significance/causation. Target line vs statistical control limits clearly separate; no formal SPC claim without method and sufficient baseline.
- Deadline risk (stretch): only explicit terminal state, as-of timestamp, due date and sufficient comparable completed cases. Minimum overdue-open list if inputs exist; remaining-time estimate optional with method, sample n and uncertainty. No actual live monitoring, no claim that unknown cases will miss deadline. Missing prerequisites -> explanatory state, hide unimplemented tools.

### Refine & Improve — Experiment & choose
- Existing FCFS queue calculation as stable basis. Generic arrival activity/lifecycle and service activity (matched interval) or explicit assumed service seconds. One eligible arrival/service per case unless policy specified; exclude ambiguous, invalid/missing observations with evidence. Model one pooled queue, identical qualified servers, FCFS, positive service time, fixed arrival vector; compare baseline/candidate with same cases and service demand for server-count change; for explicit service speed scenario use same arrivals and clearly disclose transformation. No whole BPMN network simulation. Festival preset separate. Same-input zero change identical results; queue precision regressions retained.
- Parameters and result on same page. Baseline/candidate mean/p95/max wait, finish span, throughput and staffing delta (one qualified worker/server only if explicitly assumed). Label modeled vs observed. Save scenarios, compare, apply to Rollout Plan. Parameter/scope changes invalidate stale results; no automatic overwriting edited plans. Value/effort rating and improvement backlog share Implementation records instead of duplicate state. Next cycle: new log or revise strategy; never label simulation as achieved benefit.

### Evidence Export
- Keep CSV/JSON provenance, scope, case evidence, validation exclusions, findings, targets, plans, modeled outcomes, assumptions and BPMN exports. Add new DTOs if implemented. Graph image export optional. No hidden analytics effect from display-only filters. Archive legacy data safely, not as current evidence.
