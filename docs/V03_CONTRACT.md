## 1. Scope, evidence and numeric rules

- Pass normalized, nonempty `Trace` records from one dataset and one selected process. Each case occurs once. Multi-process analysis inputs are rejected as in Phase 2, except explicit Festival counterpart links. Functions accept an empty selected trace array unless a simulation requires an input vector. Do not mutate inputs.
- The existing date controls select whole cases by the first accepted event, with inclusive bounds as currently implemented in `src/state/analysis.tsx`. `EventWindow` for replay/drift and individual history buckets are separate, half-open ranges `[startMs, endMs)`. They operate within the selected cases. Observed time extents use `[first timestamp, last timestamp + 1 ms)`. Keep the original timestamps and source order. Compare events by `(timestampMs, sourceOrder)`. For CSV, source order is the index in parsed engine rows and the UI uses `rowMap` to locate original CSV rows. XES uses the original document ordinals and locations in §3A.
- `Trace.events` includes starts. `Trace.sequence` contains only complete and point rows. Preserve existing `matchLifecycle` rules, including same case and activity, exact instance ID when supplied, otherwise one unambiguous pair. General discovery and handoffs keep unpaired completions. Measured service and matched gap remain separate from inter-event gap.
- Durations are in decimal minutes except explicit service seconds and benefit hours. Timestamps are UTC epoch milliseconds. Percentages use 0–100 and drift differences use percentage points. `Variant.share`, ROI shares, and realization use 0–1 fractions. Scores use 0–100 points. Observed throughput uses cases/bucket and modeled throughput uses cases/hour. No intermediate rounding. Serialize finite numbers only.
- `null` means a value cannot be determined or does not apply. Numeric zero represents a measured count or computed zero with a valid basis. Empty evidence arrays mean a defined set with no members. Omitted additive fields mean that the provider or saved record predates the field. New analytical APIs throw `RangeError` for invalid required configuration, mixed-process inputs or numeric overflow outside the reported series limits. The import API reports validation results as specified in §3A. Incomplete valid evidence uses the return DTO's nulls, empty arrays, or documented reasons. Window bounds, anchors and replay cursors must be safe-integer milliseconds within the JavaScript date range. An exclusive window end may be one millisecond past the maximum valid instant. Reject inverted/empty windows.
- Case evidence contains unique `CaseKey` values, even when `n` or a frequency counts multiple events per case. Keep first contributing case order from the input for new evidence arrays. `CaseKey`, variant IDs, resource IDs, and finding IDs are opaque at the presentation boundary. An `EventEvidenceRef` resolves by scoped case and `sourceOrder` and carries its UTC time. Use own-property lookups for dictionaries keyed by activity labels.
- Each saved comparison, candidate, design, scenario, or plan keeps `AnalysisScope`, provider, source provenance, linked evidence IDs, and applicable config/assumption revisions. Keep the existing workspace key and v1 archive behavior. Display filters, replay cursor, period selection, and bucket width are not whole-case filters. Save window, terminal and bucket definitions with the affected records. Avoid persisting raw rows, replay event indexes, or full interval/event payloads. Keep test fixture output distinct from results computed by the actual provider.

## 3A. CSV and XES import (P0)

Week 9–10 coverage and the KGU log exercise put XES alongside CSV in the release baseline. ProcessPilot supports a documented trace-based import subset of IEEE XES and retains the complete Phase 2 CSV path, including column mapping, preview and exclusion consent. [IEEE 1849-2023](https://standards.ieee.org/ieee/1849/10907/) · [XES Concept extension](https://www.tf-pm.org/resources/xes-standard/about-xes/standard-extensions/concept) · [XES Time extension](https://www.tf-pm.org/resources/xes-standard/about-xes/standard-extensions/time)

### Interface and accepted document form

`importXes(bytes: Uint8Array, options: XesImportOptions): XesImportResult` takes original file bytes and the existing import policy fields except `mapping`. Codex exports it from `src/engine/xes.ts` through `src/engine/index.ts`. It supplies the canonical field mapping internally, passes explicit false for an omitted `festivalValidation`, and runs the existing `validateAndNormalize` path. Accepted rows are ordinary `EventRow` values consumed through `groupCases` and the same downstream engine. The UI invokes the typed adapter from the data workspace. It chooses by case-insensitive `.csv`, `.xes` or `.xml` file suffix. `.xes` and `.xml` go through the same content validation and use no CSV mapping UI. BPMN/XML selection in Model remains separate.

- Read UTF-8 bytes with or without BOM and accept XML 1.0/1.1 declarations. Reject an invalid byte stream or a declared non-UTF-8 encoding. Accept one root `log`, with direct `trace` children and direct `event` children of each trace. Support the XES namespace `http://www.xes-standard.org/`, the common spelling without the trailing slash, and namespace-less XES. Resolve element names by local name and document namespace with prefixes permitted. Require structural children to use the same namespace as the root.
- Optional declarations `extension`, `classifier` and `global` are allowed under `log`. They are metadata. They neither load resources nor supply missing trace/event values, remap attribute prefixes or redefine activity classifiers. Document-level scalar attributes stay at log scope and do not generate case fields. Unrecognized structural elements, events outside traces, nested traces/events and mixed incompatible layouts are rejected. Empty traces yield a warning and no `EventRow`. A log without usable events cannot be analyzed.
- Accept scalar entries with `key` and `value` from `string`, `date`, `int`, `float`, `boolean`, and `id` elements. Other than the canonical field rules below, preserve the decoded lexical value as a string. Unsupported lists, containers and nested metadata outside canonical fields are skipped with a scoped warning. When nested metadata belongs to a supported scalar, retain the scalar value. A list/container occupying a canonical field or recognized Festival field is invalid for its trace/event. Do not stringify nested XML. Reject duplicate direct attribute keys at the affected trace/event scope. At log-level metadata, report malformed metadata as a document warning unless it violates structural or security rules.

Missing/blank gives `point`, as with CSV. Other values yield a row error requiring exclusion consent, including valid XES lifecycle transitions outside ProcessPilot's current lifecycle subset. |
| Event `concept:instance` or `activity_instance_id` | Optional activity-instance ID → `activity_instance_id`. Accept string identifiers and ID lexemes. Two supplied nonblank aliases must agree after the existing identifier trim. `concept:instance` is distinct from the event ID. |

Apply canonical field element types to the table above. For designated scalar Festival/resource attributes and `process_type`, retain lexical strings without numeric coercion. A missing optional scalar uses the same defaults as CSV. A missing/blank required field is an error. For two nonempty physical traces with the same normalized `[processType, caseId]`, reject the document with `xes_duplicate_trace_key` rather than merging their events. Check valid trace identities before excluding invalid event rows where identity can be resolved.

Flatten events in document trace order, then event order within each trace. Assign `EventRow.sourceOrder` the zero-based flattened ordinal including excluded event positions. `eventLocations[ordinal]` gives the original zero-based trace/event indices, including excluded positions. The parser may call normalization on a compact valid-structure vector and remap normalized rows and issue indices to document ordinals before returning. Do not renumber after exclusions. Analysis retains the current per-case timestamp sort with original document order for ties. Preview and issue display use document order. No lexicographic sorting of trace, event or instance IDs.

## 4. Core activity evidence, automation and benefit

### Activity evidence and rework

`getActivityEvidence(traces): ActivityEvidenceAnalysis` uses the same discovery sequence as the DFG and the same matched intervals as performance. Report one row per discovered activity in first-occurrence traversal order. For each case/activity let `k` be occurrences. Its contribution to extra occurrences is `max(k - 1, 0)`, including nonadjacent repeats. A repeated case appears once in the top-level numerator even when several activities repeat. The denominator is `discoveredCases`, with its own case keys. The rate is `100 × repeatedCaseKeys.length / discoveredCases`, or null with no discovered cases. Starts alone contribute neither a discovery instance nor a repeat. The generic rework Finding uses the same repeat rule. When Festival rework is explicitly configured, retain the configured Finding semantics and show its domain vocabulary separately from the generic activity evidence.

For activity service, `eligible = occurrenceCount`, `n = valid matched pairs`, and `totalMin = sum((completeMs - startMs) / 60000)` with `meanMin = totalMin / n`. Both are null at `n = 0`, and a valid zero-duration pair contributes a measured zero. The time is per activity instance, with no deduplication across overlapping instances, so it does not represent staff utilization or staffed hours. Use only matched pairs' case keys for service drill-down.

### Automation scoring

`scoreAutomation(analysis, activity, assessment): AutomationScore` scores one discovered activity against all activity rows from that same scope. Use the following definitions.

- Frequency denominator `F = max(occurrenceCount)` across all discovered activities. `f = occurrenceCount / F`. Use `S = max(service.totalMin)` across all rows with known service. When the selected activity has observed service and `S > 0`, opportunity is `100 × (f + activityServiceTotalMin / S) / 2` and basis is `frequency_and_service`. Otherwise opportunity is `100 × f`, basis is `frequency_only` and the used service denominator is null. Display frequency-only results separately from combined-basis rankings. Display service n and eligible beside any covered result.
- Suitability is `100 × (ruleBased + digitalReadiness + lowNeedForHumanJudgment) / 15` when all three inputs are assessed. Each input is an integer from 0 to 5 or null. Score is `(opportunity + suitability) / 2` when suitability exists, otherwise null. Risk and difficulty are separate from these formulas. Risk of high or null sets `requiresHumanReview` and gates automatic prioritization regardless of score. Difficulty is an integer from 1 to 5 or null. Validate finite nonnegative service and valid coverage/counts, recognized risk and known activity. No default assessment scores.
- Impact–difficulty uses user ratings 1–5, both required. Levels 4–5 are high, 1–3 low. Risk gate takes precedence. Store the matrix ratings, assessment and scoring evidence on the same activity candidate record. Any quantitative modeled impact is displayed alongside the user rating with its original unit.

### Benefit and ROI

`estimateBenefit(input): BenefitResult` uses one explicit `periodLabel` and optional single currency code (three uppercase ASCII letters). Volume is a nonnegative safe integer workload count. Shares are finite in [0,1]. Service seconds, hourly rate, and costs are finite nonnegative numbers. A user-entered independent benefit is a finite signed amount in the same period and currency. Null means missing. In service-change mode only, omitting the independent benefit means zero independent benefit.

- In `service_change`, `t0` comes from matched activity evidence with `n > 0` and finite mean (`60 × meanMin`), or from the explicit assumed seconds. An evidence row with no observed service gives a missing `t0`. With volume, eligible share and both durations, `hoursReleased = volume × eligibleShare × (t0 − expectedServiceSec) / 3600`. Negative results represent additional time. With an hourly cost and currency, `capacityValue = hoursReleased × hourlyCost`. Monetary benefit requires capacity value and explicit realization, including an explicit zero if the user assumes no realization. Then `monetizedBenefit = capacityValue × realizationFraction + independentBenefit`.
- In `financial_only`, labor values are null. Monetary benefit is the entered amount if accompanied by currency. This may refer to a scoped scenario or business assumption recorded by the UI. Waiting-time reductions are never automatically converted to labor benefit. Each independent amount must exclude any benefit already included in capacity value.
- With both cost components and currency, `totalCost = initial + recurrent` for that period. Enter an explicit zero for a cost category with none. When benefit and total cost exist, `netBenefit = monetizedBenefit − totalCost`. `roiPct = 100 × netBenefit / totalCost` only for positive total cost. If missing, `roiUnavailable` reports the first applicable reason in order `missing_currency`, `missing_benefit`, `missing_cost`, `zero_cost`. Time/capacity results remain available when their own inputs exist. Do not annualize, set a wage, or round early.

## 5. Generic queue (I-5)

`extractQueueInputs(traces, options): QueueInputSelection` takes an exact nonempty arrival activity, an optional normalized lifecycle, and observed service activity or explicit assumed `serviceSec > 0`. Omitted arrival lifecycle means complete or point. Select exactly one matching arrival per case. Observed service requires exactly one unambiguous positive start/complete pair for the named service activity with no extra rows of that activity. The service start must be at or after the arrival in event order, including permitting the arrival itself to be that start. For assumed service use the same finite positive seconds for every selected unique arrival.

Count all selected traces in `eligibleCases`. Emit either one `GateInput` per case or one exclusion, in this precedence: missing arrival, ambiguous arrival, missing service activity, ambiguous service (more than two service rows, or exactly two with the same lifecycle), invalid service (other unmatched rows, mismatched instance IDs, negative or zero duration), service before arrival. Observed mode uses canonical `matchLifecycle` and checks ambiguity before duration validity. Sort inputs by arrival and source order. Exclusion records are in input trace order. Zero inputs returns a valid selection with exclusions. The UI shows evidence and blocks the simulation with that selection.

`compareQueues(inputs, options): QueueComparison` reuses the existing decimal-precision FCFS scheduler. Inputs are the same eligible arrivals in both runs with one row per case. A server-count-only change uses identical service demands. Candidate service multiplier defaults to 1 and must be positive and finite. A different multiplier explicitly transforms each candidate duration as `baseServiceSec × multiplier`, with no selection or arrival change. Validate source order and arrivals as in the scheduler, nonempty vector, unique case keys, positive finite service and positive safe-integer server counts. Reject transformation underflow to zero and overflow. Schedule one pooled queue with identical qualified servers. Break equal availability by server index. Return the existing statistics renamed from `gateCount` to `serverCount`, with wait mean/p95/max in minutes, finish elapsed from the first arrival, and throughput `count × 60 / finishElapsedMin` in cases/hour when the span is positive. The p95 is nearest rank `ceil(0.95 × n)`. A no-change comparison returns identical numeric results. `serverDelta = candidateServers − baselineServers`, and `staffingDelta` equals that only with the explicit one-qualified-worker assumption, otherwise null.

Keep `getGateInputs`, `simulateGateQueue`, and their Festival preset behavior. Generic extraction deliberately rejects ambiguous multiple arrivals/service records. The legacy Festival extractor retains first-arrival/first-valid-pair behavior and its existing exclusions. The UI saves model family, assumptions, input config, counts/exclusion identities, scope/provider and parameters revision. Re-run after changing inputs, scope, service assumption or server configuration. Old scenarios keep their legacy gate shape. Generic plans use server delta, optional staffing delta, and exact scenario/revision identity. Drawing BPMN leaves simulation parameters and results unchanged.

## 6. Throughput and historical trends (I-8)

`getCaseThroughput(traces, options): CaseThroughputMetric` uses explicit `completion.completionActivities`. The same definition is available to replay. Nonempty labels are exact and case-sensitive. Reject duplicates and blank labels in a supplied definition. Missing definition gives null with `missing_completion`. The first complete or point row in event order matching any configured label marks completion, at most once per case. Report the configured labels and define the business meaning of the marker in the UI. A case without a marker has no recorded completion under this definition. Throughput is a completion count, with no inferred success rate or completion duration.

- Use positive bucket minutes converting to safe-integer milliseconds, with a UTC anchor. Use an epoch anchor (0) for the default UI grid. Bucket index is `floor((eventMs − anchorMs) / widthMs)`, including for times before anchor. Use exact integer floor semantics when the subtraction would exceed safe-integer precision. Buckets are half-open. Assign completion to the chosen marker timestamp. The dense series spans the buckets containing the earliest and latest accepted events across scoped traces, including starts. `observationWindow` reports the actual extent, including in an N/A result when rows exist. Empty bins in the extent mean zero recorded completions. Edge buckets can cover partial observation. There is no continuous coverage claim or series beyond the extent.
- `Metric.value` is `completedCases / bucketCount`, with `n` equal to the distinct number of cases with a marker and `eligible` equal to all selected cases. `caseKeys` lists completed cases and their assigned bucket case keys are disjoint. With configured markers and scoped rows but zero completions the result is numeric zero. With valid config and no data use `empty_scope`. If there are more than 100,000 buckets or the indices or boundaries exceed the supported numeric or UTC range use `bucket_limit`. For any unavailable result use null, a reason, `n: 0`, and empty case/bucket arrays. Invalid numeric config throws even if completion is absent. Missing completion takes precedence over empty scope/size outcomes.
- Add the distinct `case_throughput` metric through optional `KPIContext.caseThroughput` only when the caller opts into the generic series. Existing `KPIContext.throughput` and `audience_throughput` keep their Phase 2 definitions. Populate `definitionKey` for configured generic throughput even when data coverage is unavailable. Use JSON serialization of `[metricId, sortedCompletionActivities, widthMs, positiveModulo(anchorMs, widthMs)]` with deterministic code-unit sort. The key is opaque. Save it in a generic throughput `Target`. `evaluateTargets` returns unknown if one side supplies a definition key and the other does not match. Legacy metrics and targets with neither key keep existing evaluation. Targets across bucket changes require explicit re-selection.
- `getHistoricalTrends(traces, buckets): HistoricalTrends` uses the same bucket validation and density limit, with extent from earliest to latest **case first event**. A case is assigned whole to the bucket containing its first accepted event even when subsequent events lie outside the bucket. Both `caseCount` and `elapsedN` are the number assigned. `meanElapsedMin = sum(Trace.elapsedMin) / elapsedN`. `repeatN` is the count of assigned cases with nonempty discovery sequence, and repeat rate is `100 × repeatedCaseKeys.length / repeatN`. Empty denominators yield null and empty evidence. Counts in dense bins can be zero. Scope/size reasons mirror throughput. Use a comparable bucket grid and matching metric/assignment definitions across observations.

## 7. Replay, transition drift and observed patterns

### Event Log Replay

`buildReplayIndex(traces, completion?)` derives lightweight ordered event records, canonical variant IDs (null for empty discovery), positive valid matched intervals, and optional completion markers using §6. Use the full selected traces and the raw observation extent, before the replay window or variant selection. Do not synthesize lifecycle events. `getReplayFrame(index, { window, cursorMs, variantIds })` requires the cursor in the half-open window. An omitted variant filter means all cases. An empty filter means no cases. An explicit list selects exact known variant IDs, so start-only cases appear in the all-cases view. Reject unknown IDs and ignore repeated filter IDs. Frames with no selected events return zero counts, and a request window may extend past the observed data.

For each selected case find the last event at or before the cursor by ordered timestamp and source order. Every event at the cursor is applied, and the last tie becomes the latest observation. Cases without a prior row are absent from `cases` and counted as `not_yet_observed`. The lookup includes pre-window history, including a matched interval active at the window boundary. In each returned case, `active` contains all matched intervals with `startMs <= cursorMs < completeMs`. Classify once in priority order:

1. `completed` if the configured marker has been observed by the cursor. Keep the latest raw row and any active interval evidence for the inspector even if the log continues after the marker.
2. `active` if a matched interval is active.
3. `latest_observation` if a row has been observed and future rows exist.
4. `last_observation` after the final accepted row with no known completion marker yet.

State counts are exact and sum, with not-yet-observed cases, to `selectedCases`. Count cases once, even when several active intervals are displayed. Complete/point-only and unmatched-start rows describe recorded observations. A replay clock has no modeled waiting, interpolated service, or BPMN token conformance semantics. The UI owns play/pause/speed/scrub and can aggregate visible tokens or sample rendered examples with disclosure while retaining the exact engine counts and queried case detail. Cache the in-memory index per trace scope/completion definition and query by cursor/window/variant filter.

### Transition drift

`getTransitionDrift(traces, baseline, recent): TransitionDrift` requires `baseline.endMs <= recent.startMs`. Use only consecutive pairs from the selected cases' discovery sequences. Assign a pair to a period by its **destination event** timestamp. The predecessor can be outside that period but remains in the same selected case. Return rows for the union of observed directed pairs across both periods, ordered by first pair contribution in trace order. In each period:

- Count `A → B` occurrences and all outgoing occurrences from `A`. Share is `100 × count / outgoingCount` (zero if the edge is absent and the denominator is positive, null at denominator zero). Gap is the mean observed inter-event minutes for that pair, with `gapN = count`. An absent pair gives null gap and empty case keys.
- Differences are recent minus baseline. `deltaSharePp` and `deltaMeanGapMin` are calculated separately and null if either input is unavailable. For each comparison mark support `unavailable` for a null delta, otherwise `low` if either relevant denominator is below 3 (outgoing count for share, gap n for gap), otherwise `sufficient`. This is a descriptive rule. Keep raw period counts and labels on each comparison and export.

### ICN-inspired pattern evidence

`getPatternEvidence(traces): PatternAnalysis` returns observed direct edges with DFG counts and case evidence, and the following details:

- Divergence is a source activity with at least two distinct immediate destinations including self where observed. Return all its outgoing edges with their counts/case keys, the total outgoing count and contributing case union.
- Self-loops are DFG edges with equal endpoints. Count consecutive triples `A,B,A` with distinct A/B as short loops, including overlapping triples, grouped by ordered `(outer, via)` and counted once per triple. Nonconsecutive repeated activities remain visible in the rework view.
- Overlap is positive intersection of two valid matched intervals of **different** activity labels in the same case. Intersection length is `min(end1,end2) − max(start1,start2)` in milliseconds. Touching boundaries and zero-duration intervals do not count. Count each unordered interval pair once and group by code-unit sorted activity labels. For each contributing case, return the exact overlap count and one deterministic earliest example pair, ordered within each label by start event then completion event. Report matched and ambiguous pair counts from the lifecycle matcher. No inferred interval from unpaired or point events.
- The UI labels these as observed sequence, candidate alternatives, observed loops and interval overlap. Opposite orders or overlaps alone do not classify AND/XOR/OR or establish a dependency. Full ICN, ρ, gateway inference and KGU parity remain outside this interface.

## 8. BPMN comparison and lifecycle handoff

`getBpmnComparison(traces, reference, overrides): BpmnComparison` accepts a neutral process graph from the UI's BPMN import rather than XML. UI passes one selected reference process, stable BPMN element IDs and trimmed task names, plus sequence flows. Pools/lanes are displayed as presentation structure. Mark unsupported flow nodes with `kind: 'unsupported'`. If multiple executable processes are imported, require an explicit reference process before running comparison.

- Propose exact case-sensitive task-name matches against discovered activity labels. A single exact task ID yields `exact`. Zero yields `unmapped`. Multiple yield `ambiguous` with all candidate IDs. At most one override per activity. A user-selected valid task ID yields `mapped_by_user`. Explicit null yields `excluded_by_user`. Several activity labels may map to one task by user choice. Reject invalid override references, duplicate node IDs, blank IDs, and unknown flow endpoints. Mapping order follows discovery. Reference-only task IDs are tasks without any effective mapped activity. Report coverage by distinct label and discovery occurrence. Use the mapped activity case keys for drill-down.
- Minimum release is the separate As-is / observed DFG / To-be views with mapping and coverage. For adjacency, support only task, plain start/end and exclusive gateways. Allow tasks with at most one incoming and one outgoing sequence flow, one plain start with one outgoing/no incoming, each plain end with exactly one incoming and no outgoing, and XOR nodes with at least one incoming and outgoing. An exclusive split or merge may have degree greater than one on only one side. Require exactly one start, at least one end, and every node reachable from start and able to reach an end. Parallel/inclusive gateways, event variants, subprocesses, complex elements or conditional task routing are unsupported. Surface unsupported elements or unsupported structure with null checked/skipped counts and empty deviations. Mapping remains usable.
- For a supported graph, begin from each mapped task's outgoing flow and walk through silent supported nodes until another task or an end. Stop at task nodes and track visited silent nodes to handle cycles. Outgoing reachable first task IDs form the allowed adjacency set. A same-task transition needs an actual path back. Check observed DFG edges only when both effective task mappings exist. Count skipped/checked occurrences and return observations outside the allowed adjacency as deviations with original from/to, count and case keys. Ambiguous activity labels without an override remain skipped. No global fitness result or execution semantics.

The UI owns parsing/import, viewer/modeler lifecycle, To-be copy/edit/save/export, DI and revision persistence. As-is remains read-only in the comparison. To-be revisions carry `modelId`, revision number, source reference/revision, workspace scope, and linked design ID. Persist only lightweight refs with no XML persistence by default, and show explicit reload/reimport guidance. The installed bpmn-js package has a native Modeler entry point. Browser import/edit/DI roundtrip still needs validation before enabling it in production. The viewer and external edit/reimport flow provide the release fallback.
