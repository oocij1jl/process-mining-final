# ProcessPilot — Architecture & Product Spec v0.2.1
Date: 2026-11-27. This document describes the architecture leading into Phase 2. For v0.3, CSV and XES share normalized events and analysis. The v0.3 contract specifies workspace responsibilities, API integration and file ownership. [v0.3 product](V03_FINAL.md) · [v0.3 contract](V03_CONTRACT.md)

## Architecture
React + TypeScript + Vite; Tailwind, PapaParse, React Flow with layout, Recharts, bpmn-js viewer, Vitest. Static HTTPS Netlify (`npm run build`, `dist`). No backend/auth/API keys. All input processed locally. Use regular React state/context + reducer; localStorage for small workspace config only (not large raw logs or sensitive uploads). Export workspace JSON for reproducibility; import workspace not required. Browser refresh may require re-uploading dataset; restore matching settings only. English-first UI for course; Korean development documentation allowed.

## One data flow, not six unrelated pages
Raw CSV → mapping/validation → immutable normalized dataset → process + case filters → shared engine selectors → Analysis findings → Design proposal → Model targets and scenario parameters → Refine simulated alternatives → selected scenario → Implementation plan → Monitor targets and plan status → new logs trigger new cycle. Users can navigate freely. Monitor compares historical log KPIs with current targets; simulation KPIs separate, not observed. Implementation edits plan metadata, not source data or actual KPI. Never claim a proposed change was deployed.

## State ownership
- dataset: datasetId (content + mapping + exclusion policy fingerprint), sourceName, synthetic/user-upload label, validation report, immutable events, optional metadata/shifts/assets; no default Festival metadata for arbitrary imports.
- view: processKey, case/date filters, selected case, display edge threshold. Time/date filter selects whole cases by first event; never truncate traces silently. All analytical counts derive from same selected cases. Edge threshold only affects rendered graph.
- derived (not stored as independent hardcoded numbers): metrics, DFG, variants, findings, resource and handoff summaries.
- workspaces keyed by datasetId + processKey + analysisFilter fingerprint: design records, KPI targets, baseline and candidate parameters, simulation results/version, selected scenario, action plan. Dataset/filter changes mark other workspace results stale; never silently reuse incompatible scenario results. Model target edits update Monitor immediately; parameter edits invalidate candidate result until recomputed. Historical plans may be viewed/exported as archived; cannot be passed off as current.
- design records: id, proposal/finding IDs, current BPMN ref, optional To-be BPMN ref, editable change note, affected activities, target KPI, status. BPMN XML is a modeled business artifact, not a discovered DFG. Generic upload without BPMN shows upload/empty state; no unrelated demo BPMN.
- scenarios: id, designId, dataset/process/filter ref, assumption version, baseline & candidate inputs, computed KPIs; selectedScenarioId. Target changes update evaluation but not simulation physics. Candidate parameter changes mark result stale. Plan source explicitly simulated or proposal-only; new scenario creates new revision or explicit confirmation to replace; retain user edits for unchanged scenario.

## File ownership / startup
First scaffold once (student or designated lead), install packages, commit shared types/API contract. `src/contracts.ts` + `src/engine/index.ts` signatures owned by Codex and agreed before UI work. Codex: src/engine, tests, optional scripts; Claude: src/components, pages, app state, styles, viewer, integration adapters; common build config only one owner. Use separate branches/worktrees; no simultaneous edits of App/config/package lock. `public/datasets/` and `public/bpmn/` owned by business/data track. If assets not ready, small labeled hand-authored fixture, not pretend full dataset. Real Festival sample later replaces fixture. Integrate on main, run tests/build. See AGENT_HANDOFF.md.

## Festival scope and optimization
Three process types separately mined. Stage prep KPI handover→ready excludes performance duration. Equipment correlation by festival_id + performance_id (within dataset), compare readiness deadline to actual ready. Audience linked by festival/time bucket only, never infer individual show attendance. No arbitrary cross-role reassignment; only compare shared pool with explicit resource IDs, schedules/skills, otherwise workload by role. Actual utilization requires shifts and valid intervals. Scenario MVP is FCFS pooled audience gate model with identical gates, one qualified worker per gate assumption, same per-entrant service demand and arrival vector on both sides; use observed matched service interval for modeled service station or explicit user-entered duration, never assume whole entry cycle is service. See FUNCTIONAL_SPEC.md and DATA_SCHEMA.md.

## P0 graph visualization
Reuse one React Flow graph component for DFG and directed resource handoff network. Render from engine outputs only: resource nodes use stable known IDs, directed edges use handoff count and contributing case keys. Show edge counts and relative width, zoom/pan, node/edge selection with contributing cases, and empty state when no eligible handoffs exist. Include known resources even if isolated. Show reverse edges separately and distinguish them visually. Do not label as exact KGU WTN or actual communication. Graph threshold and image export remain P1; handoff CSV/table remains P0.

## Definition of done
All six lifecycle menus support a real interaction; analysis is genuine, design record editable, targets update Monitor, scenario affects plan. Build + unit/integration tests pass, external link works, exports reproduce evidence, no invented stats. Day 1 scaffold/contracts/import/DFG/early deploy; Day 2 remaining P0 plus festival data; Day 3 QA, finish gaps and release before 23:00. These are planned milestones, not elapsed-time guarantees.
